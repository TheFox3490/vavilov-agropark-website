# Проблема с сетью в WSL: зависание AAAA-запросов DNS

Документ для передачи в сессию, где чинится сеть. Все цифры — реальные замеры,
снятые 2026-08-01 в этом WSL-дистрибутиве.

## Краткая формулировка

**AAAA-запросы (IPv6) к резолверу WSL не получают ответа и висят до таймаута.
A-запросы отвечают мгновенно.** Приложения, которые резолвят имя штатным способом
(сразу A и AAAA), получают +10…20 секунд на каждое разрешение имени.

Это не проблема пропускной способности. Передача данных быстрая — стоит только
разрешение имени.

## Окружение

- WSL2, ядро `6.18.33.1-microsoft-standard-WSL2`
- `/etc/resolv.conf` сгенерирован WSL автоматически:
  ```
  nameserver 10.255.255.254
  search neoflex.ru
  ```
  `10.255.255.254` — NAT-шлюз WSL, который проксирует DNS в хостовую Windows
- В WSL **нет глобальных IPv6-адресов и нет маршрута по умолчанию для IPv6**
- `/etc/gai.conf` пустой — действуют умолчания glibc
- На хостовой Windows работает Happ VPN в режиме TUN
- Сетевую проблему в самой Windows уже чинили, там стало быстро. В WSL — нет

## Замеры

### Разрешение имени раздельно по типам записей

| Имя | Только A (`getent ahostsv4`) | Только AAAA (`getent ahostsv6`) |
|---|---|---|
| `www.figma.com` | **0,11 с** | **20,09 с** |
| `s3-alpha-sig.figma.com` | **0,11 с** | **20,08 с** |
| `static.figma.com` | 0,11 с | 0,11 с |

При обычном разрешении (`getent ahosts`, оба типа сразу) `www.figma.com`
стабильно занимает **11 с**, причём повторный запрос столько же — результат
не кешируется.

### Разбивка HTTP-запроса по фазам

```
https://www.figma.com/favicon.ico
   DNS 11,03 с | TCP +0,20 с | TLS +0,06 с | первый байт +0,07 с | итого 11,37 с
```

Видно, что **весь простой приходится на `time_namelookup`**. TCP-рукопожатие,
TLS и передача занимают доли секунды.

Из-за этого показатель «скорость скачивания» вводит в заблуждение: curl честно
делит объём на общее время и рисует ~900 Б/с, хотя сама передача идёт быстро.
При массовой загрузке (45 файлов) это давало сквозные ~19 КБ/с, потому что
каждый файл начинался с 11-секундного залипания на DNS.

### Принудительный IPv4 полностью снимает проблему

| Запрос | Обычный | С флагом `-4` | Ускорение |
|---|---|---|---|
| `www.figma.com/favicon.ico` | 11,59 с | **0,32 с** | ×36 |
| `api.figma.com/v1/me` | 11,34 с | **0,47 с** | ×24 |

## Что проверено и исключено

- **Не проблема канала.** `registry.npmjs.org` резолвится за 0,008 с и отдаёт
  8,6 МБ/с. Сборка Docker-образов (pip, npm, docker pull) идёт на полной скорости.
- **Не специфично для Figma.** Несуществующее имя `<случайное>.npmjs.org`
  висит те же 20 с. Проблема в типе запроса, а не в домене.
- **Не виноват `search neoflex.ru`.** Имя с завершающей точкой
  (`www.figma.com.`, поиск суффикса отключён) даёт те же 11,05 с против 11,04 с.
- **Не тормозит резолвер как таковой.** `example.com` и `static.figma.com`
  отвечают за 0,11 с по обоим типам записей.

## Наиболее вероятная причина

Имена, у которых **есть настоящие AAAA-записи** (`www.figma.com`,
`s3-alpha-sig.figma.com`), не получают ответа на AAAA — пакет теряется где-то
на пути WSL → `10.255.255.254` → резолвер Windows → TUN-туннель Happ.

Имена **без AAAA-записей** (`static.figma.com`, `example.com`) отвечают
мгновенно, потому что ответ NODATA короткий и, судя по всему, доходит нормально.

Отсюда рабочая гипотеза: теряются или отбрасываются именно ответы, содержащие
IPv6-адреса. Дальше копать имеет смысл в сторону обработки AAAA на стыке
WSL-NAT и TUN-интерфейса Happ.

Цифры 10 и 20 секунд складываются из умолчаний glibc: `timeout:5`, `attempts:2`.

## Обходные пути (по возрастанию радикальности)

1. **`options single-request-reopen`** в `/etc/resolv.conf` — заставляет glibc
   слать A и AAAA не параллельно в один сокет, а последовательно в разные.
   Иногда этого достаточно.
2. **Отключить AAAA для приложений** — например, `precedence ::ffff:0:0/96 100`
   в `/etc/gai.conf`, чтобы IPv4 всегда выигрывал. На сам факт AAAA-запроса
   не влияет, поэтому помогает не всегда.
3. **Свой резолвер в WSL** — прописать `nameserver 1.1.1.1` напрямую, отключив
   автогенерацию через `/etc/wsl.conf`:
   ```ini
   [network]
   generateResolvConf = false
   ```
   Обходит хостовый резолвер целиком. Проверить, ходит ли DNS мимо TUN.
4. **Починить обработку AAAA в Happ/TUN** — единственное настоящее решение.

Важно: обходной путь должен работать не только для `curl`, но и для Python
(`urllib`), Node и Docker, иначе часть инструментов останется медленной.

## Как проверить, что починилось

```bash
time getent ahostsv6 www.figma.com
```

Должно отработать за доли секунды, а не за 20. Дополнительно:

```bash
curl -s -o /dev/null -w 'DNS %{time_namelookup}с итого %{time_total}с\n' https://www.figma.com/favicon.ico
```

`time_namelookup` должен стать околонулевым.

## Что от этого зависит в проекте

Скрипт `tools/figma_assets.py` докачивает 24 оставшиеся картинки макета
(21 из 45 уже на диске). Каждая картинка = одно разрешение имени = 11 секунд
простоя. После починки докачка займёт минуты.

Запуск после починки:

```bash
python3 tools/figma_assets.py && python3 tools/figma_map_assets.py
```
